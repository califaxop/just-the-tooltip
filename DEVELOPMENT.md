# Just the Tooltip!: development notes

Just the Tooltip! (JTT) improves the game's own tooltip for WoW: Forever (Interface 16001, a
Midnight 12.x client running Classic content). It positions the tooltip, restyles it and adds a
few lines, and never replaces it, so every addon that writes to the tooltip keeps working. This
file holds the architecture, conventions, milestone plan and progress.

- Game and addon APIs, with how each was verified: [API_COMPATIBILITY.md](API_COMPATIBILITY.md).
- Other addons JTT works with: [INTEGRATIONS.md](INTEGRATIONS.md).
- The companion source data: [SOURCE_DATA.md](SOURCE_DATA.md).
- Player-facing changes: [CHANGELOG.md](CHANGELOG.md).

## Conventions

- **Evolve, don't rewrite.** `JustTheTooltipDB` keeps its shape and old saved settings load.
- **Modify the game's tooltip, never replace it.** Lines are added after the game's and other
  addons' own; nothing removes another addon's lines.
- **No unverified API.** No API, event, field or return position is used before it's checked.
  [API_COMPATIBILITY.md](API_COMPATIBILITY.md) labels each one **Verified in WoW Forever**,
  **Verified by source / documentation**, **Inferred but untested** or **Unsupported**. Untested
  behaviour is never reported as verified.
- **Secret values.** Game calls whose answer can be hidden go through `ns.Safe` (1.6.0). Missing,
  erroring or secret values come back as nil, so a detail that can't be read is left out and the
  rest of the tooltip carries on. Hidden values are never worked around.
- **One failure stays local.** Each information category (ID, item level, sources, target line,
  colours) fails on its own.
- **Hooks are installed once.** Each hook group goes through `ns.Once(key)`; `ns.hooks` lists
  what's installed.
- **Other addons' settings.** Changes JTT makes to another addon's setting (NeedRoll's tooltip
  lines, Auctionator's vendor line) last for the session only. They're put back before logout,
  unless the player changed that setting themselves meanwhile.
- **Lightweight.** No work happens while no tooltip is up. The update driver runs only while it
  has something to do.
- **Hygiene.** No unused code or settings. Offline tests (`tests/run_tests.py`) cover the logic;
  game behaviour is checked in game (checklists below), never claimed from the tests.

### Start-up

ADDON_LOADED loads the settings and builds the settings window. PLAYER_LOGIN then runs
`Anchor.Hook`, `Look.Hook`, `Info.Hook`, `Sources.Hold` (NeedRoll's lines off),
`HoldOthers` (Auctionator's vendor line off) and `Look.Refresh`. PLAYER_LOGOUT runs
`Sources.Release` and `ReleaseOthers`, putting the other addons' settings back.

### A tooltip, start to end

1. Something calls `GameTooltip:SetOwner` (the `Stop()` and `ghost = false` hook). A tooltip at
   the default spot calls `GameTooltip_SetDefaultAnchor` (`OnDefaultAnchor`): JTT follows the
   cursor, places it at your spot, or watches the frame it belongs to.
2. The game fills it, and `TooltipDataProcessor` post-calls add JTT's lines per data type (Item,
   Spell, UnitAura, Unit, Corpse, Object).
3. On show, `Look.Paint` styles it.
4. The driver (an `OnUpdate`, shown only while needed) follows the cursor. It also hides world
   tooltips once the mouse leaves what they're about (`UPDATE_MOUSEOVER_UNIT`,
   `WORLD_CURSOR_TOOLTIP_UPDATE`, `C_TooltipInfo.GetWorldCursor`, the interface under the mouse).
5. On hide: `Stop()`, and a "ghost" mark if it was a world unit or thing.

Lifecycle state (1.7.0): one record, `Anchor.state` (S), described field by field at the top of
`Anchor.lua`.

| Moment | What happens to S |
|---|---|
| `SetOwner` (every new tooltip starts with it) | `Fresh()`: a new `gen`; unit, thing, ghost, cursor, focus and owner facts cleared; watching stopped |
| `GameTooltip_SetDefaultAnchor` | placement: `following` (cursor), your spot, or `owner` (a frame, watched); a placement check a frame later |
| Unit / Corpse / Object post-call | `unit` / `thing`; world ones start `watchUnit` / `watchCursor` and remember `startFocus` |
| driver | follows; `CheckOwner` (seen, then off for 0.1 / 1.5 s, or the frame hidden); interface under the mouse; mouseover gone; cursor over nothing |
| `UPDATE_MOUSEOVER_UNIT`, `WORLD_CURSOR_TOOLTIP_UPDATE` | a world tooltip left over: leave (hide, or the game's fade) |
| `OnHide` | watching stopped; `ghost` if it showed a unit or thing; unit, thing, focus cleared |
| `OnShow` | a ghost (no new owner since) hidden again (with "no fade") |

The two older names stay as `A.Stop` and `A.Fresh`. The timers (`lastX`, `lastY`, `sinceCheck`,
`sinceUI`, `sinceThing`) belong to the driver, not to a tooltip.

## Milestone 1 audit (1.5.0 source)

### Traces

**Item level.** `Info.OnItem` → `ItemLevel(tip, link)` → `C_Item.GetItemInfo or GetItemInfo`.
- The return positions are correct: item level 4th, equip location 9th, class ID 12th (12
  returns: name, link, quality, item level, required level, type, subtype, stack size, equip
  location, icon, sell price, class ID). Equip This!'s engine reads the same positions, verified
  in WoW: Forever, and warcraft.wiki.gg documents the same order (nil while the item isn't cached).
- The investigation target ("incorrect positions") isn't a defect. The `pcall` result shifts every
  return by one, and the old code accounted for that.
- Gear is decided by class (2 weapons, 4 armor) and equip location, never by level alone.
- 1.6.0 moves this into a pure `Info.GearLevel(level, equipLoc, classID)`, tested for weapons,
  armor, shields, jewelry, bags and quivers, non-equipment, and incomplete or hidden answers.
- An uncached item gets no line. The game shows the tooltip again when the item's data arrives
  (Inferred; in-game check 3).

**Cursor.** `OnDefaultAnchor` → `FollowCursor(true)`; then each mouse move, from the driver.
- The point is `SetPoint(corner, UIParent, "BOTTOMLEFT", x / tooltipEffectiveScale, ...)`.
- A point's offsets are in the scale of the frame being placed, not of the frame it's placed
  against. Dividing the cursor by the tooltip's own effective scale is therefore correct at any
  tooltip or UI scale. Verified by documentation (warcraft.wiki.gg, SetPoint: "increasing the
  Region's scale will increase the offset"; GetCursorPosition: "unaffected by UI scale") and by
  source: What's Training places its Forever menu the same way.
  The investigation target ("should use UIParent's scale") would have been wrong at any size but
  100%.
- The defect: the distance from the cursor was added in the tooltip's units, so it grew and shrank
  with the Size slider (defect 3).

**Sources.** `Info.OnItem` → `Sources.Add(tip, id)` → `Lines(id)`.
1. `Lines` uses the companion's data (`Data()`, loaded on demand, tried once a session).
2. If the item isn't there, it asks Questie (`FromQuestie` → `QuestieDB()`).
3. `Lines` keeps the result per item for the session.
4. NeedRoll's lines are read from a hidden scan tooltip (`FromNeedRoll`) and also kept per item.

Questie's states, as handled in 1.6.0:

| Questie | 1.5.0 | 1.6.0 |
|---|---|---|
| Not installed | asked again each time | `absent`: asked again each time |
| Loading: its API says not ready | asked again | `loading`: asked again, nothing kept |
| Loading, item lookup not bound yet (Questie before 12.9 bound it while starting up) | gave up on Questie for the session and kept "no sources" for that item (defect 5) | `loading`: asked again, nothing kept |
| Ready | used | `ready`: used, results kept |
| Ready, no item lookup | gave up | `unusable`: kept (it won't change) |

Questie 12.9 and 12.11 bind `QueryItemSingle` as QuestieDB loads and set `Questie.API.isReady`
(verified by source). In-game check 5 confirms the current Questie.

## Known limitations (2.0.0)

- Only tooltips the game puts at its default spot move. Tooltips anchored beside a bag slot,
  window or button stay where the game puts them.
- Drop order follows Classic 1.12's loot tables (CMaNGOS), which may differ on WoW: Forever, so
  chances never show on tooltips. NeedRoll's newer dungeon lines replace JTT's where it has them.
- Sources: up to 12 named per kind and item, the rest counted. NeedRoll names 3 per item.
- Places come from QuestieDB's first spawn in the zone; creatures with several spawn points show one
  of them. None inside dungeons.
- Item levels need the item's data from the server: an item not yet loaded gets its level once the
  tooltip fills in.
- "How many you have" includes the bank only after you've opened it this session.
- In combat the game hides some unit details from addons. Those lines (target, colours, NPC ID)
  are left out rather than guessed.
- Pressing the detail key over an open tooltip redraws it where the game allows
  (`tip:RefreshData`); otherwise the details show on the next hover.
- Other tooltip addons (TipTac, TinyTooltip, ElvUI...) may also move or restyle tooltips.
  `/jtt compat` counts tooltips moved after JTT placed them.
- Duplicate checks read the tooltip's text in English: another addon's item level, target or ID
  line in another language isn't recognised (both would show).
